# FrameForge AI 智能体编排与知识库开发文档

## 1. 目标与范围

本次改造面向“输入一章小说，自动得到漫剧成片”的无人值守流程。流程覆盖故事导入、语义知识索引、角色与剧集规划、场景和镜头拆分、图像生成、视频生成、配音、质检、时间线和 MP4 渲染。用户只需要提交故事正文；运行期间不需要逐镜头审批。

本次重点解决两个问题：知识库不能按固定字符硬切导致上下文破碎；自动编排不能因为视觉模型对背景人物、服装或画风的主观判断而反复重试并最终失败。

## 2. 总体架构

```text
故事正文
   │
   ├─ StorySource（MySQL）
   ├─ 语义切块 → Embedding → Qdrant（项目/工作空间隔离）
   │                         │
   │                         └─ Director 检索上下文
   │
   └─ Director AUTOPRODUCE
        │
        ├─ DashScope LLM 生成 ProductionPlan
        │    └─ 角色 → 集 → 场景 → 镜头
        ├─ GenerationJob + OutboxEvent（可靠排队）
        ├─ Dispatcher → Celery Worker
        │    ├─ IMAGE
        │    ├─ VIDEO
        │    └─ VOICE
        ├─ 技术校验 + 可选视觉质检
        └─ Timeline 五轨渲染 → MinIO MP4
```

API 负责写入业务事实和任务队列；Dispatcher 只负责投递；Worker 负责调用 Provider、保存资产和回写状态；`automation.py` 是可恢复协调器，按照数据库状态推进下一种媒体任务。任何服务重启后，Dispatcher 都能从未完成的 `AgentRun` 和 `GenerationJob` 继续运行。

## 3. 知识库语义切块

### 3.1 原问题

旧实现使用固定字符窗口：从第 N 个字符开始截取固定长度并重叠。它会把叙事段落、对白和动作说明从中间截开，造成检索结果缺少主语或上下文。故事修改后，旧版本向量也没有明确替换，可能让检索同时命中新旧内容。

### 3.2 新策略

实现位于 `backend/app/rag/service.py`：

1. 统一换行和空白，只把连续空行当作段落边界。
2. 优先按完整段落合并，默认目标长度为 1400 字符。
3. 单个段落超过目标长度时，按中文句号、问号、感叹号和分号切成完整句子。
4. 没有标点的异常长段落才使用字符窗口作为最后兜底。
5. 在跨段落硬边界处保留最多 180 字符的句子级尾部上下文，避免人物或动作突然断开。
6. 每个 Qdrant 点写入 `chunk_index` 和 `chunk_count`，方便调试、评估和后续邻接块扩展。

兼容性方面保留了 `chunks = semantic_chunks` 别名，旧脚本和调用方无需立即改名。

### 3.3 版本与重建

故事内容发生变化时，现在会：

- 将旧 `KnowledgeVersion` 标记为 `SUPERSEDED`；
- 创建递增的知识版本并更新 `current_version_id`；
- 按 `document_id` 删除 Qdrant 中旧点；
- 重新计算当前版本的语义块和向量。

这保证了检索结果只来自当前故事版本，同时保留 MySQL 版本记录用于审计。

## 4. 自动制作编排

### 4.1 计划阶段

`POST /api/v1/projects/{project_id}/director/runs` 接收 `intent=AUTOPRODUCE` 和正文。Director 使用 DashScope LLM 输出严格 JSON 的 `ProductionPlan`，并由 Pydantic 校验角色、集数、场景数、镜头数、时长以及角色引用。计划合规后一次性创建故事、角色版本、剧集、场景、镜头和首批图像任务。

### 4.2 媒体阶段

协调器按镜头依次确认 IMAGE、VIDEO、VOICE：

- 没有任务则创建任务；
- 任务排队或运行中则等待；
- 任务完成则检查资产；
- 过期租约通过 OutboxEvent 恢复投递；
- 所有镜头就绪后创建五轨时间线并调用 FFmpeg 渲染。

每个任务都带 `agent_run_id`、资源 ID和幂等键。这样 Worker 重启、Dispatcher 重启或网络短暂中断不会重新创建一套孤立任务。

### 4.3 质检分层

技术错误仍然是阻断条件：Provider 明确失败、资产缺失、下载失败、FFmpeg 渲染失败都会使运行失败并留下警告。

视觉模型对“背景人物算不算角色”“青色和蓝色是否一致”“手部是否符合某种画风”等判断属于软性意见。现在这类结果写入 `run.warnings` 和审计数据，但不会阻止无人值守成片。视觉模型不可用时标记 `UNVERIFIED`，也不会误判为质量失败。用户仍可在审核页查看这些提示并人工复核。协调器会对轮询期间重复出现的同一条视觉提示去重，并限制保存数量，避免长任务把相同警告写入数百次，影响真正问题的定位。

## 5. 已修正的问题

### 5.1 页面转圈和项目找不到

根因包括 Docker 引擎重启后 API 端口未恢复，以及浏览器保存的旧会话已被撤销。修复方式是恢复 Compose 服务，并让前端 401 自动走 refresh；用户需要在会话彻底失效时重新登录。

### 5.2 自动协调器访问空任务

旧协调器假设每个镜头始终存在 `GenerationJob`，在任务尚未创建的瞬间访问 `inspection_json`，触发 `NoneType` 异常。现在发现任务为空会重新排队，并把生产状态保存在数据库。

### 5.3 视觉质检误报导致重试耗尽

视觉模型曾把青角鹿、背景弟子和父子一起出现判为角色数量错误，也曾把风格化手部判为缺陷。现在质检报告仍保留，但模型意见不再消耗自动重试次数；只有 Provider 和渲染链路的技术故障阻断流程。

### 5.4 知识版本污染

旧故事重新索引时会留下旧向量，且内容变化直接报错。现在采用版本递增、旧版本失效、按文档删除旧点后重建的流程。

### 5.5 时间线派生资产

最终 MP4 没有对应的 GenerationJob，旧逻辑把运行 ID当成任务 ID写入，导致长度或外键约束问题。渲染资产现在明确使用 `source_job_id=None`，并由 `AgentRun` 和时间线记录来源。

## 6. 测试与验证

本次新增 `backend/tests/test_rag_chunking.py`，覆盖：

- 段落在目标长度内时保持完整；
- 超长内容按句子边界分割并保留邻接上下文；
- 非法 overlap 参数被拒绝。

已执行并通过：

```text
python -m pytest -q backend/tests/test_rag_chunking.py   3 passed
docker compose exec -T api ruff check app tests        All checks passed
docker compose exec -T api python -m compileall -q app
```

此前已验证的自动制作链路也完成过真实 DashScope 成片：8 个镜头、1 集、包含视频、配音、字幕和最终 MP4。当前服务通过 Docker Compose 运行，API、Worker、Dispatcher、MySQL、Redis、Qdrant、MinIO 和前端均已启动。

## 8. 后续建议

生产环境可以继续增加检索评估集、按章节标题提取结构化元数据、对相邻语义块做可配置扩展，以及把“技术阻断”和“内容警告”在前端分成两个独立状态。默认切块参数应根据实际小说平均段落长度做一次离线评估，再决定是否调整到 1200 或 1600 字符。
